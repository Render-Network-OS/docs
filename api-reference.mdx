This page is a catalogue of RNDRNTWRK’s documented interface design. It describes operation names, their intended responsibilities, and the information an integration needs to handle.

The route symbols below are design references, not a deployment-specific API contract. For a specific integration, use its product documentation for the host, supported operations, authentication, and exact request and response schemas.

Placeholders such as `{id}`, `{epoch}`, and `{wallet}` identify a resource within a route. Their format, validation, and permitted use belong to the selected integration.

## Authentication Model

The documented account model includes Sign In With Solana, or SIWS: a client obtains a challenge, asks a wallet to sign the sign-in message, and submits the result for verification. The design then associates subsequent requests with an authenticated session.

A signing request needs to make its purpose clear to the participant. The wallet handles signing; the application uses the resulting signed message.

The integration defines session creation, expiry, logout, and which operations an account may perform. Account sessions, service webhooks, and operator controls have different authority requirements. People and agents act within the permissions assigned to them.

## Authentication

| Documented symbol | Intended role and data |
|---|---|
| `POST /auth/nonce` | Obtain the challenge used in the sign-in design. |
| `POST /auth/verify` | Submit signed sign-in information for verification and session creation; the documented result includes the associated wallet address. |
| `POST /auth/logout` | End an account session and clear its client-side session state. |
| `GET /me` | Read the account associated with the session, including its participant reference and relevant account metadata. |
| `POST /auth/social/link/start` | Begin linking a social account to the authenticated account; the design includes a redirect or verification challenge. |
| `POST /auth/social/link/verify` | Complete social linking using the response required by the selected provider integration. |

The session-cookie and social-linking details need to match the chosen service. A session reference identifies an account context; individual actions still depend on that account’s permissions.

## Arcade & Gaming

This family connects games, sessions, scores, saved state, and rankings. An experience’s rules define valid participation and how results are interpreted.

| Documented symbol | Intended role and data |
|---|---|
| `GET /game/{id}/rank` | Account-scoped rank for a game, with score and percentile information. |
| `POST /arcade/score` | Submit a score for checking and recording under the game’s rules; retain the submission result and its relationship to the leaderboard. |
| `GET /arcade/state` | Arcade presentation state, such as theme, event information, and display metadata. |
| `GET /arcade/cabinets` | Cabinet descriptions, game identifiers, display metadata, and any recorded control or possession state. |
| `GET /game/{id}/state` | Read saved game state associated with the account and game. |
| `PUT /game/{id}/state` | Save game progress and retain the service’s recorded outcome. |
| `POST /game/{id}/record` | Submit a completed run or match record, with its session and result context. |
| `POST /game/{id}/play` | Record the start of a play session for the specified game. |
| `GET /game/{id}/leaderboard` | Per-game rankings. The documented filter is `period`, with `day`, `week`, `month`, and `year` as design values. |
| `GET /game/{id}/stats` | Aggregate game information, such as play counts and participant counts. |
| `GET /game/referral/leaderboard` | Referral-activity rankings presented in the game-leaderboard format. |

A score submission, an accepted result, and a point entry describe different steps. Points are interpreted under the experience’s terms. The [VAP guide](/protocol/vap) describes participation-record verification.

Cabinet control also needs the authority of the relevant creator or operator. Reading a cabinet’s state and changing its game session are separate responsibilities.

## Battles

The battle design covers creating an instance, finding instances, and joining a chosen game session.

| Documented symbol | Intended role and data |
|---|---|
| `POST /battle/create` | Create a battle description with its game configuration, instance identifier, and joining information. |
| `GET /battle/active` | List battle records by their recorded joinable or in-progress state. |
| `POST /battle/{id}/join` | Request participation in a battle and obtain the resulting participant/session state. |

The game’s rules need to define who may join, when entries close, and how the application handles a full, ended, or interrupted battle.

## Lottery

The round-based design includes round descriptions, entries, result selection, and supporting records. Each experience would define its entry rules, permitted operators, selection method, and treatment of interrupted rounds.

Prize allocations, reward claims, and payout records belong to [SW4P Earn](/products/earn).

**Current status: SW4P Earn is not yet publicly available. No staking, liquidity, reward, or claim programme is currently open.**

### Round and entry records

The catalogue documents an earlier `/round` family alongside a `/chat/round` family.

| Documented symbol | Intended role and data |
|---|---|
| `POST /round` | Describe a proposed round and its configuration. |
| `POST /round/{id}/ticket` | Describe an entry request and any associated payment reference under the round’s terms. |
| `POST /round/{id}/finalize` | Describe a finalisation request for the authorised round controller, including selection and result records. |
| `GET /round/{id}` | Round metadata, recorded status, entries, and any programme prize information. |
| `GET /chat/round/active` | The round identified as active in the chat-round records, or an empty result. |
| `GET /chat/round/{id}/entries` | Entry records associated with a chat round. |
| `GET /chat/round/recent-finalized` | Summaries of rounds recorded as finalised. |
| `GET /chat/status` | Chat-round connection and operation status information. |

### Results and supporting records

| Documented symbol | Intended role and data |
|---|---|
| `GET /chat/round/{id}/winning-numbers` | The recorded selection result and information explaining its derivation. |
| `GET /chat/round/{id}/audit` | The round’s activity and selection record, including references to randomness, entries, and checks where the design uses them. |
| `GET /chat/round/{id}/entries/root` | A Merkle-root reference for the recorded entries in a design that uses that representation. |
| `GET /chat/round/{id}/winners` | The selected recipients and the programme amounts recorded against them. |
| `GET /chat/round/{id}/payouts` | Programme payout state and associated transaction references. |

Selection records and payment records need to remain connected to the same round. The application should distinguish a selected result, an allocation, and a confirmed payment.

Chat-round creation and start controls belong to the operator responsibilities described under [Admin](#admin).

## Leaderboards

Leaderboard records describe rankings under a specified scoring model and reporting period.

| Documented symbol | Intended role and data |
|---|---|
| `GET /leaderboard/global` | Combined rankings from the experience’s chosen score sources. The documented query names are `period`, `limit`, and `offset`. |
| `GET /leaderboard/global/stats` | Aggregate participation and score information for the combined leaderboard. |
| `GET /leaderboard/global/period-stats` | Aggregate information for the requested `period`. |
| `GET /leaderboard/global/rank` | The account’s position, score, and percentile in the combined ranking. |
| `GET /leaderboard/quests` | Rankings based on the quest-point records selected by the experience. |
| `GET /leaderboard/quests/rank` | The account’s quest rank and point total. |
| `GET /leaderboard/quests/stats` | Aggregate quest-leaderboard information. |

The documented period values are `day`, `week`, `month`, and `year`. An integration needs to define the period boundaries, score sources, pagination, and visibility rules it uses.

## Rewards

This family describes financial programme records and proposed claim operations within [SW4P Earn](/products/earn).

SW4P Earn extends SW4P’s economic model into source-aware allocation, claims, rewards, payout schedules, reserves, and reconciliation.

**Current status: SW4P Earn is not yet publicly available. No staking, liquidity, reward, or claim programme is currently open.**

The symbols below preserve the documented reward-interface design. A future programme would supply its eligible activity, funding source, allocation rules, recipients, claim timing, supported network and addresses, effective date, and support path.

### Epoch and proof records

| Documented symbol | Intended role and data |
|---|---|
| `GET /api/rewards/epoch/{epoch}/proof/{wallet}` | A proposed record connecting a recipient and epoch to an allocation proof. The documented data includes a proof, amount, and leaf index. |
| `GET /api/rewards/epoch/{epoch}` | Epoch metadata, including a root reference, total, status, and timestamp in the documented model. |
| `GET /api/rewards/epochs` | An ordered list of epoch summaries. |
| `GET /api/rewards/epochs/committed` | Epoch records classified by a recorded chain commitment. |

The programme would define the proof representation and the meaning of each epoch state. A commitment record and a completed payment have distinct meanings.

### Claims and recipient records

| Documented symbol | Intended role and data |
|---|---|
| `POST /api/rewards/claim` | A proposed claim-submission operation that associates a recipient, epoch, and proof with the programme’s claim process. |
| `GET /api/rewards/wallet/{wallet}/claimable` | Proposed recipient allocations grouped by epoch and amount, according to programme eligibility and claim state. |
| `GET /api/rewards/wallet/{wallet}/claimable-epochs` | The recipient’s epoch records filtered by the programme’s claim and settlement rules. |
| `GET /api/rewards/wallet/{wallet}/projected` | An estimate in the programme design, with the assumptions and calculation that produced it. |
| `GET /api/rewards/wallet/{wallet}/pending-usdc` | A proposed record of USDC-denominated amounts still outstanding in the programme. |
| `GET /api/rewards/pool/today` | Programme funding and allocation information for a defined reporting period. |
| `GET /config/rewards` | The programme’s allocation configuration and distribution rules. |

An estimate, an eligible allocation, a submitted claim, and a confirmed payout need separate records. The selected programme would explain the transitions between them, including any off-chain settlement record.

## Referrals

The referral design connects a shared reference with an account and the activity attributed to it.

| Documented symbol | Intended role and data |
|---|---|
| `GET /api/referral/link` | Obtain the account’s referral link and code. The documented design also considers initialising a link when one is absent. |
| `POST /api/referral/link` | Create an account-associated referral reference. |
| `POST /api/referral/bind` | Associate the account with a referrer. The documented design allows one referrer binding per wallet. |
| `GET /api/referral/summary` | Referral counts and any associated participation-point totals. |
| `GET /api/referral/stats` | The account’s detailed referral-activity measures. |
| `GET /api/referral/referred` | Referred-account references and the times those relationships were recorded. |

An integration needs to make link creation, binding rules, visibility, and duplicate handling clear. Referral activity is a reporting input; any financial referral programme would use SW4P Earn’s funding and allocation terms.

## Profile & Daily Tasks

Account records can bring together participation, ranks, linked accounts, task state, and payment history.

| Documented symbol | Intended role and data |
|---|---|
| `GET /api/profile` | The account profile, participation-point records, rank, and linked accounts. |
| `GET /api/profile/beta-points` | Point totals and their breakdown in the beta context. |
| `GET /api/profile/beta-stats` | Activity statistics in the beta context. |
| `GET /api/beta/preference` | The account’s recorded beta-mode preference. |
| `POST /api/beta/preference` | Change the account’s beta-mode preference. |
| `GET /api/tasks/daily` | Task definitions and the account’s recorded completion state. |
| `POST /api/tasks/daily/complete` | Submit a task-completion report for checking under the experience’s rules. |
| `GET /api/me/payments` | The account’s payment-history records, including amounts, timestamps, and recorded outcomes. |
| `GET /users/{wallet}/stats` | Participant statistics made visible under the application’s sharing rules. |

The interface needs to identify the environment to which a preference or record belongs. Points, task completion, and payments remain distinct: a task report is checked under the experience’s rules, while a payment record describes an economic operation.

## Events & SSE

Server-Sent Events, or SSE, lets a service send updates over a persistent connection.

| Documented symbol | Intended role and data |
|---|---|
| `GET /events` | The documented event-stream design uses `text/event-stream` and JSON event data. Subjects include chat entries, messages, round transitions, battle results, and system notices. |

Named examples in the design include `new_entry` and `chat_message`. An integration needs to define subscription authority, event fields, reconnection, and how a client catches up after an interruption.

| Documented symbol | Intended role and data |
|---|---|

| `GET /events/burn/{id}/leaderboard` | Rankings based on the event’s recorded burn amounts. |
| `GET /events/burn/{id}/leaderboard/referrals` | The referral-associated portion of the event rankings. |
| `GET /events/burn/{id}/leaderboard/game` | The game-associated portion of the event rankings. |

Event creation and activation are operator responsibilities. A burn record, participation points, and a programme reward represent different actions and records; any reward programme belongs to SW4P Earn’s model and current programme status.

## Eligibility & Configuration

Eligibility is specific to a product, feature, or participant role. Getting started with RNDRNTWRK requires an internet-enabled device; a particular experience may define further access conditions.

| Documented symbol | Intended role and data |
|---|---|
| `GET /eligibility` | An eligibility result for the applicable access rules, with relevant holding information where those rules use a token. |
| `GET /config/normalization` | The experience’s score-normalisation parameters and caps. |
| `GET /config/games` | Game identifiers, names, and category mappings. |

## Wallet & Webhooks

| Documented symbol | Intended role and data |
|---|---|
| `POST /api/wallet/resolve` | The wallet-resolution design associates a supported identifier, such as a name-service entry or linked social handle, with an address. |
| `POST /webhooks/payment-status` | A service-to-service payment-status receiver that associates an incoming update with the original payment record. |

An identifier resolution needs the selected integration’s identity and address rules. Payment updates need the authorised sender and the payment context required to interpret the result.

[Hyperlink](/protocol/hyperlink) describes the payment-request interaction. [SW4P](/sw4p) coordinates settlement and its confirmed outcome. An application uses those payment records to determine whether its payment requirement has been met.

## Admin

Operational controls belong in a service’s operator reference, with explicit authority for the affected system and action.

The documented responsibilities include:

| Area | Operator responsibility |
|---|---|
| Arcade presentation | Configure themes and one-time presentation events |
| Cabinet control | Assign or release game-session control within the creator’s or operator’s permitted scope |
| Round administration | Configure and start chat rounds; manage authorised finalisation |
| Scheduling | Start, stop, and inspect a round scheduler |
| Quest administration | Create, inspect, change, remove, or correct quest records under an assigned administrative role |
| SW4P Earn operations | Prepare or import programme distributions and record settlement outcomes under the programme’s rules |
| Beta records | Inspect environment-specific points and define any authorised migration or conversion handling |
| Service diagnostics | Interpret health signals, record errors, and inspect the state needed to resolve an issue |

These are operational design subjects. The operator documentation defines the controls, credentials, and procedures appropriate to the service.

## Error Responses

The documented error model includes a human-readable `error` message. An integration defines the full error envelope and any additional fields a client should retain.

| Status | Meaning in the documented design |
|---|---|
| `400` | Missing or invalid request information |
| `401` | Authentication is missing or invalid |
| `403` | The caller lacks the required permission |
| `404` | The requested resource was not found |
| `409` | The request conflicts with an existing state, such as an existing binding or recorded operation |
| `500` | The service encountered an internal failure |

A client should distinguish an input problem, an authority problem, and an interrupted operation. Retaining the relevant request and operation references helps the user follow the appropriate next step.

## Rate Limiting

Use the chosen service’s documented limits for polling, event connections, and writes. Request scheduling should account for the service’s response and any retry instructions it supplies.

Where an event stream is supported, it can deliver changes without repeatedly requesting the same state. Reconnection and missed updates still need defined handling.

For a write or payment request, establish the existing operation’s state before choosing a retry or continuation. [@sw4p/kit](/products/kit) describes that relationship for settlement integrations.
