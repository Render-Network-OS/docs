# sw4p

**sw4p is the settlement engine of RNDRNTWRK.** It turns fragmented cross-chain value movement into a single settlement layer for routing, gas abstraction, and execution. Instead of exposing bridges directly, sw4p resolves the route, coordinates settlement, and tracks the transaction through completion.

sw4p matters because value gets trapped behind fragmented rails, different fee models, and chain-specific logic. That makes cross-chain settlement operationally heavy, expensive to integrate, and hard to standardize across products. sw4p gives the network a single settlement primitive so cross-chain movement becomes operational rather than exceptional.

| **Custody** | User flows are non-custodial — users sign from their own wallet. |
| **Fee model** | Transparent 50 bps pricing with path-specific minimums |

## How It Works

sw4p starts from the outcome, not the bridge choice.

1. A client expresses the settlement intent
2. sw4p resolves the best available route for the token and corridor
3. The engine provisions gas where needed and coordinates execution
4. Settlement is tracked through a persistent 15-state lifecycle until completion
5. Recovery logic handles retries, stalled transfers, and partial failures

For native USDC corridors, the current production flow is:

**Burn → Attest → Mint**

No wrapped tokens. No liquidity pool dependency. No manual bridge selection for the end user. The USDC on the destination chain is native Circle USDC.

## Routing and Settlement

sw4p is the settlement layer. Callers express the outcome they want — "send X USDC from chain A to recipient on chain B" — and the engine resolves the route, provisions gas, executes the move, and tracks the transaction through completion. Underlying rails are an implementation detail of the engine, not a choice the caller has to make.

The engine is designed around ERC-7683-compatible intents, making competitive solver-based execution a first-class expansion path.

## Advanced Capabilities

Beyond basic cross-chain transfers, sw4p includes:

- **DCA (dollar-cost averaging)** — schedule recurring buys with best-execution SPL routing on Solana
- **Limit orders** — price-triggered fills monitored by a background worker
- **Agent API** — batch settlement, cross-chain portfolio aggregation, rebalance planning and execution
- **Solver auction framework** — ERC-7683-compatible intent system with competitive filler execution
- **Universal storefront** — multi-tenant storefront with per-project config and custom subdomains
- **Fiat on-ramp** — Transak integration with webhook settlement
- **Referral system** — referral codes with automatic fee splitting
- **Telegram and Discord bots** — conversational bridge interface

## Security

sw4p is hardened as a settlement system.

The stack includes rate limiting, authentication, circuit breakers, fee audit logs, configurable security policies per route, and observability across the full settlement lifecycle. The gas abstraction layer ships with 1,743+ adversarial tests. Settlement state is checkpointed with explicit recovery actions for every stalled transition.

End-user flows are non-custodial — users sign from their own wallet. The engine never holds user balances; settlement is native at both endpoints. Internal signing materials used for protocol-side execution are managed by sw4p infrastructure and are not exposed to integrators.

<Note>
  **Supported production asset:** USDC. The $555 token is a Solana SPL token and is not bridged by sw4p. Any USDC-to-555 conversion is explicit product policy, not an implied default.
</Note>
